# 读一个区，写一条回复

写回复是这个工具里唯一需要判断的写入。这份文件讲：怎么量一个区、怎么写、怎么自测、发出去之后怎么读结果。

## 量这个区

```bash
xx comment section --status <id> --scrolls 3
```

返回四组东西：

| 字段 | 是什么 |
| --- | --- |
| `length` | 回复长度的 median / p25 / p75 / min / max |
| `questions` | 多少条在提问 |
| `led` | 拿到最多赞的 5 条，带各自的 `wit` 判定 |
| `shape` | `has-a-point` / `flat` / `generic-praise` 各多少 |
| `subject` | 这个区在聊什么（见下） |
| `top` | 最受赞的那一条及其 `stance` |

**它的作用是让你知道这里的正常回复长什么样**，不是让你写得像。写多长、写多具体才不算突兀，取决于这里的人。

### `subject`：这个区在聊什么

| `stance` | 意思 | 怎么用 |
| --- | --- | --- |
| `about_work` | 在聊帖子本身 | 顺着帖子说，引用作者是对的 |
| `about_self` | 在说自己的情况 | 只跟着附和读起来像没读；说帖子本身会更突出 |
| `asking` | 在提问 | 直接回答一个问题就是最合适的动作 |
| `spam` | 在卖东西 | 没什么可参与的对话 |

`dominant` 是多数派，`note` 用一句话说这意味着什么。`comment list` 的每条也带自己的 `stance` 和 `signals`。

**同样长度的两条回复，一条在聊作品、一条在说自己，引用错了就是错位。** 对着 `about_self` 的回复说「说得好」，等于告诉所有人你没读。

**这是按措辞判的，不是按意思判的。** 一条回复可以点了题却在说自己。`signals` 是判定所依据的词，你可以不同意——不同意就自己读那几条。

## 写

没有工具能替你写，也不该有。工具能给的是「写完怎么检查」。

写完先自己过一遍楼上一个区的数字：长度在 `p25`–`p75` 之间了吗？这个区有没有人提问，我问了会不会突兀？

然后跑：

```bash
xx comment check --status <id> --draft "…"
```

### `check.verdict`

| 值 | 意思 | 该做什么 |
| --- | --- | --- |
| `has-a-point` | 有具体指认、有第一人称立场、或有个转折 | 可以发 |
| `flat` | 没具体的东西，也没立场 | 补一句只有读过这条才说得出的 |
| `generic-praise` | 大部分是「太牛了」「学到了」「很有价值」这类放到哪条都成立的话 | 重写 |

### `check.sameness`

拿这条草案跟**你已经发过的回复**（本地历史里确认成功的）比的：

| 值 | 意思 |
| --- | --- |
| `varied` | 开头、结尾、长度都在变 |
| `narrowing` | 开始趋同了——`note` 会说哪一部分重复 |
| `template` | 已经是同一个模子。**换角度，不是换词** |
| `too-few` | 发过的还不到三条，比不出来 |

它比的是开头几个字、结尾几个字和长度，**不是意思**。所以 `template` 的解法不是换个说法，是换一个真正不同的切入点——同一句话换个同义词还是同一个模子。

`note` 会点名是什么重复了（「4 条里 3 条以『删除。』结尾」）。如果你不同意，就去看那几条。

### `check` 是报告不是闸门

它不会拦你，**过了也不等于写得好**。它只测「像不像空话」和「像不像上次那条」，测不了：

- 观点对不对
- 有没有编造
- 是不是真的回答了这条

那些你自己核。

## 发

```bash
xx comment post --status <id> --text "…" --request-id reply-<id>-01
xx comment reply --status <id> --comment-id <reply-id> --text "…" --request-id reply-<id>-02
```

**`--request-id` 必须给，每次新的发送用新的 id。**

第一次跑会返回 `needs_approval`——工具**什么都没发**，把原文和目标摊给你看。把 `text` / `target` 原样给主人，停下等回复，同意了再用同一个 id 加 `--confirm` 重跑。

发之前 `--dry-run` 检查参数（不开浏览器）：

```bash
xx comment post --status 123 --text "…" --request-id t-1 --dry-run
```

### 结果怎么读

| 返回 | 意思 |
| --- | --- |
| `confirmed: true` + `result.evidence` | 发出去了。`toast` 是平台提示；`new_row` 是页面上新增了一行、文字完全一致、且作者是本账号 |
| `replayed: true` | 这个 request id 之前就成功了，没有重发 |
| `delivery_uncertain` | **按了按钮但页面没给证据。可能已经发出去** |
| `idempotency_conflict` | 同一个 request id 配了不同文字 |
| `identity_mismatch` | 弹窗不是回复模式，或回的账号不对。**什么都没打进去** |
| `draft_conflict` | 输入框里有别人留下的草稿，被保留了 |
| `needs_confirmation: true` | 半小时内发得有点多，停下来问。看过之后加 `--confirm` 继续 |

**`confirmed: true` 就是发出去了。** 它已经核对过正文、目标、本人标记和页面证据。再跑一次 `comment list` 去「确认一下」不会让它更真。

**弹窗关掉不算证据。** 页面在发送成功后会关弹窗，用户按 Esc 或者发送被拒也会关。所以只有弹窗关闭时返回的是 `delivery_uncertain`，不是成功——`uncertainty_reason` 会是 `composer_closed_without_new_row`。

### 测试功能不要拿陌生人的帖子当试验田

「测试一下」「验证能否发送」这类句子出现在真实帖子下面会让人莫名其妙，而且公开、撤不回。要验证链路就用自己的帖子或 `--dry-run`。

## `delivery_uncertain` 绝不自动重发

它可能已经出现在时间线上，再发就是两条。

1. 先确认页面没有登录/验证遮罩（有遮罩时读到的是旧页面）。
2. `xx comment list --status <id>` 看你的文字在不在。窗口是加载出来的，**没看到不等于没发出去**。
3. `xx receipt get <request-id>` 看回执停在哪。
4. 真的没发出去，才用**新的** request id 重来，并告诉主人这是新的一次。

**三个容易误读的地方：**

- `history list` 只记**确认成功**的发送。一条 `delivery_uncertain` 的回复**不会**出现在里面。所以「历史里没有」不能当作没发出去的证据。
- 回执停在 `dispatching` 有两种可能：还在确认中，或者就是那次 uncertain。光看状态分不出来，要看 `uncertainty_reason` 和 `updated_at`。
- 回执里的 `tweet_id` 可能指向一个已被删除的帖子，打开会 404。这不代表回执错了，只代表目标没了。

找不到是哪一条时，直接问主人要链接、id 或那次用的 request id。**不要从回执里挑一条时间最近的当成他说的那条。**

## 节奏

一条一条来。读完一条、想清楚、再写下一条。

**没有值得说的话就不发**，这是常态不是失职。工具不提供随机间隔或拟人节奏的参数——那是在让平台看不出你在做什么，不是在帮你写得更好。
